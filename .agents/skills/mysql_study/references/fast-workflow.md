# 分级研究执行参考

只在开始、继续或收束一个研究专题时读取。简单状态查询和 Git 提交不需要本参考。

## 1. 先定级，再写结论矩阵

在 idx 写 `- 研究级别：S|D|R|M`。S 级判定见 SKILL.md；S 级不能因为赶时间自动降为 D。

在工作记录中先定义，不必单独形成永久文件：

| ID | 待证明结论 | PG 预期 | MySQL 预期 | 行为观察 | 路径观察 | 源码入口 |
|---|---|---|---|---|---|---|
| C1 | 一句话、可证伪 | 行为 | 行为 | 用户可见结果 | LSN/状态/页/等待/错误 | 文件/函数候选 |

合并语义重复的结论。实验或源码不能影响最终迁移判断的内容不要纳入主线。

## 2. 一次性预检

用一个批次确认：

- 两个实例版本、连接和专题对象是否存在；
- 当前 Git 状态，识别用户已有修改；
- 资源限制与需要恢复的全局变量；
- 可复用的已有 evidence、文章或源码索引。

预检结果只保存与专题结论相关的版本/参数，不保存整段环境输出。

## 3. PG 基线不是概念摘要

先在 `/data/myfuture/src/func/` 检索同主题文章。对 S 级提取 PG 的入口、结构体、调用链、状态变化和
可观测点；核对 PG 18.4 本地源码，旧文章只作为心智基线，不能把版本过时的函数名、参数或理论数字
直接带入新文章。D/R/M 只提取会改变迁移结论的 PG 路径。

## 4. 源码研究：从锚点升级为执行模型

先搜索函数/枚举/错误文本，再沿调用者与被调用者读取窄窗口。D 级至少串起：

1. 决策入口；
2. 决定差异的条件分支；
3. 必要时再加执行或报错入口。

核心机制不能只留一个枚举定义而缺少决策逻辑；必要时增加执行/错误出口。支撑事实通常只需一个锚点。
默认不要保存完整文件、连续数百行源码或所有搜索命中。源码 evidence 要写明版本、路径、函数和行号。

### S 级六层展开

| 层 | 必答问题 | Evidence |
|---|---|---|
| 入口 | 谁在何时、哪个线程/进程调用？ | 上游调用点与入口函数 |
| 结构 | 操作哪些核心对象和字段？生命周期归谁？ | struct/class/enum 窄窗口 |
| 执行 | 主路径逐步做什么，输入/输出是什么？ | 连续调用链，不是函数名列表 |
| 状态 | 关键字段如何变化，保持什么不变量？ | 状态转换表及赋值/判断代码 |
| 分支 | 哪些条件导致跳过、等待、降级、回滚或失败？ | 条件分支与错误出口 |
| 观测 | 如何从日志、SQL、状态、文件、LSN 或 GDB 看到？ | 本次真实输出或明确未实测 |

先画调用链骨架，再填结构和状态；缺少中间环节时继续追调用，不用文章措辞掩盖断点。关键源码可在
正文保留短小片段，重点逐行解释状态改变；大段原码留在本地源码，不复制进 evidence 充数。

## 5. 双引擎实验

- 两边使用相同表结构、初始数据、事务顺序和观察指标；
- setup 与 cleanup 各一份，所有实验复用；
- 会话并发使用明确同步点，不依赖人工猜时间；
- 阻塞实验在确认 wait 状态和锁证据后立即 COMMIT/ROLLBACK 释放；
- lock timeout 只作为保护栏，不把等到 timeout 当作常规实验步骤；
- 捕获失败时保留原错误码/SQLSTATE，并验证事务后续状态；
- 一项观察已能排除其他解释时停止追加相似实验。

### S 级必须双实验

- **行为实验**：同一输入和故障/并发顺序，两边验证提交、可见性、错误码或恢复结果。
- **路径实验**：建立能排除“碰巧得到同一结果”的内部证据。例如记录 checkpoint/commit/crash LSN，
  证明恢复扫描区间；记录 wait point；观察恢复事务/undo 数量；触发并捕获目标错误分支。

路径实验开始前写清要制造的状态关系，例如 `checkpoint_lsn < commit_lsn <= flushed_lsn < crash_lsn`。
实验结束按关系逐项核对。只有最终 SELECT 结果、只有进程日志出现 ready，均不能证明 redo/复制/优化器
等内部路径。无法制造路径证据时把结论降为“源码确认，实验未验证”，专题不得写成已完整实测。

原始输出可完整留在单个 raw 文件，但文章只引用关键几行和结论。交互提示符、重复表头和无关状态可以机械清理。

## 6. MySQL 实操先形成可执行稿

写文章前先整理一份可重复执行的 MySQL 操作稿，至少包含：

- 连接命令及前置条件；
- 按顺序执行的 SQL/shell 命令；
- 多会话的 T1/T2 时序；
- 每一步关键预期、错误码或判断标准；
- cleanup/rollback；没有状态变更时明确写“无需清理”。

操作稿进入 evidence，同时完整写入文章 `## MySQL 实操：命令与 SQL`。文章不能只给片段或
“其余见 evidence”。PG 操作必须实测并留档，但正文默认只保留关键结果。

## 7. 一次写作，多处投影

先形成唯一的结论表：

| 维度 | PG | MySQL | 迁移含义 | 证据 |
|---|---|---|---|---|

然后从它派生：

- 文章：解释“为什么”和实验结果；
- idx：状态、完成项、资产入口、下一步；
- pg-mysql-map：仅新增此前没有的映射；
- runbook：仅新增生产可执行命令或处置判断；
- roadmap：只更新状态和一句产出；
- verification：默认省略，用户要求或理解风险高时才建，通常 5～8 题。

不要在这些文件中重复完整机制说明。

## 8. 分级写作模板

### S 级源码专著

正文标题文字可以调整，但必须可识别地覆盖：

1. 问题边界与结论矩阵；
2. PG 基线与现有心智模型；
3. 完整调用链；
4. 核心数据结构；
5. 状态变化与关键分支；
6. 行为实验；
7. 路径实验；
8. 源码—实验—生产映射；
9. `## MySQL 实操：命令与 SQL`；
10. 未验证范围与 Evidence。

完整调用链至少标明入口、关键中间阶段和出口；数据结构不能只报名字；映射表至少能从每条核心结论
追到源码状态和真实观察。S 级不设置文章/源码 evidence 行数上限，评审长文时删除重复，不删除机制链。

### D/R/M

D 沿用精简对照文章；R 以生产操作及恢复护栏为主体；M 只做稳定映射和最小验证。三者仍强制
MySQL 完整实操，但不伪装成源码专著。

## 9. 深度与速度如何同时保持

深度保留在：

- 核心机制的因果链，而不是长源码摘录；
- 会改变结论的边界条件，而不是相似实验堆叠；
- 真实失败形态和恢复方法，而不是泛化描述；
- 可执行的 MySQL 操作，而不是命令名称清单。

速度来自一次 setup、批量读取、可控并发、同一结论表派生多份资产，以及证据充分后立即停止。
恢复/复制/性能专题按需要增加故障注入或重复测量，其他部分仍保持收敛。

## 10. 完成条件

同时满足即可停止：

- 结论矩阵全部有真实观察，或明确记录无法验证的原因；
- PG/MySQL 实验具有可比性并可复现；
- 关键 MySQL 结论有本地源码锚点；
- 文章含完整 `## MySQL 实操：命令与 SQL`，新手可以照顺序执行并判断结果；
- 文章能从结论表追溯到 evidence；
- 临时对象、会话和参数已清理；
- `scripts/validate_topic.sh <专题目录>` 通过。

S 级还必须满足：六层源码模型闭合；行为与路径实验都有真实观察或明确未验证；每条核心结论能追溯
到“源码状态变化 → 实验观察 → 生产含义”。validator 只做结构性下限检查，人工复核仍要确认内容真实。

完成后汇报结论、资产路径、清理状态和未决风险。除非用户明确要求，不提交 Git。
