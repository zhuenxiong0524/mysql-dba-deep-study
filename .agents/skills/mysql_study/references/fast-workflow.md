# 深度快跑执行参考

只在开始、继续或收束一个研究专题时读取。简单状态查询和 Git 提交不需要本参考。

## 1. 先写结论矩阵

在工作记录中先定义，不必单独形成永久文件：

| ID | 待证明结论 | PG 预期 | MySQL 预期 | 最小实验 | 源码入口 |
|---|---|---|---|---|---|
| C1 | 一句话、可证伪 | 行为 | 行为 | 同一数据/并发顺序 | 文件/函数候选 |

合并语义重复的结论。实验或源码不能影响最终迁移判断的内容不要纳入主线。

## 2. 一次性预检

用一个批次确认：

- 两个实例版本、连接和专题对象是否存在；
- 当前 Git 状态，识别用户已有修改；
- 资源限制与需要恢复的全局变量；
- 可复用的已有 evidence、文章或源码索引。

预检结果只保存与专题结论相关的版本/参数，不保存整段环境输出。

## 3. 核心机制深挖，支撑事实收敛

先搜索函数/枚举/错误文本，再读取窄窗口。核心机制优先串起：

1. 决策入口；
2. 决定差异的条件分支；
3. 必要时再加执行或报错入口。

核心机制不能只留一个枚举定义而缺少决策逻辑；必要时增加执行/错误出口。支撑事实通常只需一个锚点。
默认不要保存完整文件、连续数百行源码或所有搜索命中。源码 evidence 要写明版本、路径、函数和行号。

## 4. 双引擎实验

- 两边使用相同表结构、初始数据、事务顺序和观察指标；
- setup 与 cleanup 各一份，所有实验复用；
- 会话并发使用明确同步点，不依赖人工猜时间；
- 阻塞实验在确认 wait 状态和锁证据后立即 COMMIT/ROLLBACK 释放；
- lock timeout 只作为保护栏，不把等到 timeout 当作常规实验步骤；
- 捕获失败时保留原错误码/SQLSTATE，并验证事务后续状态；
- 一项观察已能排除其他解释时停止追加相似实验。

原始输出可完整留在单个 raw 文件，但文章只引用关键几行和结论。交互提示符、重复表头和无关状态可以机械清理。

## 5. MySQL 实操先形成可执行稿

写文章前先整理一份可重复执行的 MySQL 操作稿，至少包含：

- 连接命令及前置条件；
- 按顺序执行的 SQL/shell 命令；
- 多会话的 T1/T2 时序；
- 每一步关键预期、错误码或判断标准；
- cleanup/rollback；没有状态变更时明确写“无需清理”。

操作稿进入 evidence，同时完整写入文章 `## MySQL 实操：命令与 SQL`。文章不能只给片段或
“其余见 evidence”。PG 操作必须实测并留档，但正文默认只保留关键结果。

## 6. 一次写作，多处投影

先形成唯一的结论表：

| 维度 | PG | MySQL | 迁移含义 | 证据 |
|---|---|---|---|---|

然后从它派生：

- 文章：解释“为什么”和实验结果；
- idx：状态、完成项、资产入口、下一步；
- pg-mysql-map：仅新增此前没有的映射；
- runbook：仅新增生产可执行命令或处置判断；
- roadmap：只更新状态和一句产出；
- verification：默认省略，用户要求或理解风险高时才建，通常 5～8 题。

不要在这些文件中重复完整机制说明。

## 7. 深度与速度如何同时保持

深度保留在：

- 核心机制的因果链，而不是长源码摘录；
- 会改变结论的边界条件，而不是相似实验堆叠；
- 真实失败形态和恢复方法，而不是泛化描述；
- 可执行的 MySQL 操作，而不是命令名称清单。

速度来自一次 setup、批量读取、可控并发、同一结论表派生多份资产，以及证据充分后立即停止。
恢复/复制/性能专题按需要增加故障注入或重复测量，其他部分仍保持收敛。

## 8. 完成条件

同时满足即可停止：

- 结论矩阵全部有真实观察，或明确记录无法验证的原因；
- PG/MySQL 实验具有可比性并可复现；
- 关键 MySQL 结论有本地源码锚点；
- 文章含完整 `## MySQL 实操：命令与 SQL`，新手可以照顺序执行并判断结果；
- 文章能从结论表追溯到 evidence；
- 临时对象、会话和参数已清理；
- `scripts/validate_topic.sh <专题目录>` 通过。

完成后汇报结论、资产路径、清理状态和未决风险。除非用户明确要求，不提交 Git。
